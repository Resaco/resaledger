## Notes

- `ci` reads the merge base, the base and the head (for a push, before and after) each in the `dir` of its own valid configuration, or the base's when theirs is invalid or missing. Every other rule stays the base's. Removed decisions and log entries are matched by name across the two folders.
- `enforcement.mjs` now reads the merge base's decisions in the merge base's own folder. Without this, an old decision that moved with the workspace counted as new, and an old `- Weakens: dir` let the move through.
- The gates check gets the head's `dir`, so in stamp mode the stamp is looked for, and the code fingerprinted, the way the head's own `verify` wrote it.
- Not changed: `checkRange` (range.mjs, T4.7's lane) still reads each commit's tasks and code paths with the base's `dir`. A commit naming a task after the move fails until the move is on the base. Spec 10 and the team guide say to make the move alone, with `Task: maintenance`.
- Found while writing the guide: after a move, a plain `update` keeps the hooks and the `AGENTS.md` block as changed by hand, because they name the old folder. The guide says to use `update --force`.
