- **The lane rule follows merges.** A commit reached only through a merge's second parent was made on another branch, so judging it as the current lane's is wrong: after a lane merges into the base, or after a migrated lane is merged, `check --range` on the base refuses commits that name a task their own lane held. - **Double claims.** The guides and spec 6.3 say CI reports a task held in two open branches; `ci` has no such check. Report a task that this pull request holds while another branch in the clone holds it under a different lane, or change the guides and spec to what is true.

## Notes

The lane rule accepts a task whose Lane is another lane's on a commit reachable from that lane's branch, read as T4.4 reads it (`laneBranches`, moved to `range.mjs` so `ci` and the range check share it). The rule does not look at the first-parent chain: a lane's own commits pass wherever a merge, a fast-forward or a stacked branch puts them, and any other commit that names that lane's task fails, also on the first-parent chain. So the base passes after merging a lane twice, a side branch cannot launder a commit, and a stacked lane cannot commit code for the holder's task. When the lane has no branch in the clone (merged and deleted, or a renamed branch), the old rule decides: a Lane set inside the range passes, one held at the start fails. commit-msg keeps the old rule, which already refuses the stacked case there, as HEAD holds the task.

Cost: nothing extra for a range that names no other lane's task; otherwise one `git for-each-ref` and one `git rev-list --parents` for the whole range. The for-each-ref pattern `refs/remotes/*/<lane>` replaces T4.4's `git remote` call, as `*` matches one path segment; a remote whose name has a slash is no longer seen. On a 200-commit merged lane the check took about 0.1 s more, within noise on a loaded machine.

Double claims are checked: in a pull request, a task the lane holds that another branch not merged into the base holds as another lane fails the ownership check, unless the head records a takeover from that lane. One `git for-each-ref --no-merged` and one `git cat-file --batch`, only when the lane holds a task.

Changed: `src/guard/range.mjs`, `src/guard/ci.mjs`, `src/guard/ownership.mjs`; spec 5.9, 6.3 and 10; the module rows; the CI and concepts guides. A commit that names a task of an existing lane but is not on its branch now gets the new message instead of the "held before this range" one; the bundle test of `check --range` was updated for that.
