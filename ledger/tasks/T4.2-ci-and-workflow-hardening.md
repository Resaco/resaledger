## Notes

- Finding 2: `runGates` takes `options.env`, and `ci` passes its own environment without `GITHUB_TOKEN` and `ACTIONS_*` (which covers `ACTIONS_ID_TOKEN_*`). The comment is still posted after the gates by the same process. This keeps the token out of the gates' environment, not out of their reach: on Linux a gate can read its parent's initial environment in `/proc/<pid>/environ`, and a background process can outlive the gates. Only a separate job for the comment puts the token beyond them; spec 12 now says so.
- Finding 7: the gates do not run at all when the working tree is not at the head; the note stays and the problem says to check out the head. The acceptance test now runs `ci` in each lane's worktree, as CI does.
- Finding 11: `ciCommand` treats every error from `ciOptions` or `ciResult` as a check that could not run.
- Finding 15: the template uses `actions/checkout@v5` and `actions/setup-node@v5`, `timeout-minutes: 30`, and a concurrency group per pull request (or ref) that cancels only pull request runs. It is not pinned by SHA: without the web the SHAs cannot be looked up, a released template has one hash for every repository, and a pin goes stale with each release of the action. The team guide says how to pin by SHA, why, and that a pinned workflow is a hand edit that needs a decision naming `workflow`.
